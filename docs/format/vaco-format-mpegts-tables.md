# `vaco-format-mpegts-tables`

Layer 4. MPEG-TS packet framing and the PSI/SI **section layer**: the
188-byte transport packet, the adaptation field, the CRC-32, section
reassembly, descriptors, PAT/PMT/CAT/SDT, `stream_type` resolution and DVB
text.

This is not the demuxer. `vaco-demux-mpegts` is, and it is built on this
crate. Everything here takes a `&[u8]` a caller already has: no I/O, no
policy, no opinion about which packet to emit next. It registers nothing —
it is a shared helper, like `vaco-format-isom`.

---

| `crc` | the MPEG-2 section CRC-32, and only that |
| `section` | `SectionHeader`, `Section`, `SectionAssembler` — `pointer_field` handling and packets that span |
| `descriptor` | the descriptor loop plus the dozen descriptors that change observable output |
| `psi` | `Pat`, `Pmt`, `Cat`, `Sdt` |
| `stream_type` | `TsCodec`, `from_stream_type`, `from_registration`, `resolve`, `for_codec` (the mux direction) |
| `text` | DVB text decoding (ISO 6937 and the selectable tables) |
| `write` | PAT/PMT/SDT and descriptor **writers** — the mux direction of `psi`/`descriptor` |

### The two properties the whole crate holds to

**No I/O.** Every entry point takes a slice. That is what lets the entire PSI
stack be fuzzed without constructing a file, and it is why the demuxer — not
this crate — owns the sync-byte search.

**No allocation from a length field.** The only buffer in the crate is
`SectionAssembler`'s fixed 4 KiB array, sized by the twelve-bit
`section_length` field's own ceiling rather than by anything an input
declares. Everything else is a borrowed view. So there is no input to this
crate that can make it allocate: plan 13 §2.2.2's dominant bug class is
removed by construction rather than bounded.

## How it works

### CRC-32 — four parameters, all four load-bearing

Polynomial `0x04C1_1DB7`, initial value all-ones, **no reflection** in or out,
**no final XOR**. Getting any one of them wrong makes every section fail
rather than obviously break, and the reference discards a failing section
*silently* — so the symptom is a missing program, not an error.

Running the CRC over a whole section *including* its own trailing four bytes
yields zero. `section_crc_ok` is that check and is all a caller needs. The
256-entry table is generated by a `const fn` from the polynomial: spec-dictated
data under D15, so it is merger material and is derived here rather than
transcribed. A unit test cross-checks it against the bitwise definition, and a
property test asserts that every single-bit error in every position is caught.

### Section reassembly

A section may begin anywhere inside a packet's payload, may span any number of
packets, and may share a packet with the tail of its predecessor. The
`pointer_field` on a `payload_unit_start_indicator` packet says where the *new*
section begins; everything before it belongs to the one in progress.

`SectionAssembler::push(pusi, payload, callback)` is the whole interface. It
calls back once per complete section, possibly several times for one payload
and often not at all.

**`abandon()` clears the alignment, not just the partial section.** That is the
non-obvious half, and a property test is what found it. Keeping alignment
across a continuity gap makes the assembler read the *middle* of the next
section as a header — the shrunk counterexample was a section whose body was
zeros, which frames as an endless run of three-byte sections — and emit tables
nobody sent. The CRC would reject them, but only after the framing had spliced
unrelated bytes together, and a private section carries no CRC at all. After
lost bytes the only correct answer is to wait for the next `pointer_field`.

**The assembler is total; the header parser is not.** A long-form section can
declare a `section_length` smaller than its own eight-byte header —
`01 80 00` is the shortest example, found by `mpegts_section` on its 30th
execution. The framing layer is right to hand those three bytes over; the
*table* parsers are what refuse them. So `Section::new` returns `Option`, and
the invariant to rely on is that anything eight bytes or longer parses.

### Descriptors — what earns a typed accessor

A descriptor gets one when it changes an **observable** field: the codec a
`stream_type` resolves to, a stream's language, a disposition flag, or — for
teletext and DVB subtitling — how many streams one PID produces. Everything
else stays as bytes, because parsing a structure nothing reads is attack
surface bought with no output.

### `stream_type` resolution

Two stages, in order: Table 2-34 first, then the descriptor loop. `0x06`
("PES packets containing private data") is by a wide margin the commonest value
in real DVB and ATSC multiplexes and on its own means nothing; a registration
descriptor or a DVB codec descriptor is what identifies it.

A registration identifier never overrides an unambiguous `stream_type` —
except in the private range `0x80` and up, where the identifier is
*definitionally* stronger because the range's meaning depends on which
organisation's assignment applies.

### Writers — the mux direction (added for FM-25, issue #576)

`write::build_section` is the one function every table writer calls: it takes
a `table_id`, `table_id_extension`, `version` and a body, and produces a
complete section with `current_next_indicator` set and a correct trailing
CRC-32 — the exact inverse of `SectionHeader::parse` plus `crc32`.
`write_pat`/`write_pmt`/`write_sdt` build the body bytes on top of that, and
`service_descriptor`/`registration_descriptor`/`build_descriptor` do the same
for the three descriptor shapes a muxer needs. None of them span a table
across more than one section (see *What this deliberately does not do*
below) — a body that would not fit returns `None` rather than truncating.

**Every writer is tested by feeding its own output back through the reader
on the same page** (`Pat::parse`, `Pmt::parse`, `Sdt::parse`,
`DescriptorIter`) — the strongest check available when both directions live
in one crate, because there is only one place for the two to quietly agree on
a wrong byte. `vaco-mux-mpegts` then checks the same bytes a second time, end
to end, by demuxing its own muxer's output with `vaco-demux-mpegts`.

`stream_type::for_codec(codec, dvb)` is the mux-side mirror of `resolve`:
given a `vaco_codec_core::CodecId` and whether to conform to DVB System B or
ATSC System A, it returns the `stream_type` (and, in the private `0x06`
range, the `registration_descriptor` identifier) a muxer should write. It is
tested by asserting the round trip through `resolve` directly — with one
documented exception carried over from `from_stream_type` itself:
`stream_type` `0x03` states only "MPEG-1 Audio", not which layer, so
`CodecId::Mp1` and `CodecId::Mp3` both write `0x03` and both read back as
`TsCodec::Mp2` until something parses the actual frames. AC-3/E-AC-3/DTS
round-trip under **both** conventions: ATSC's own `stream_type` values
(`0x81`/`0x87`/`0x8A`) and DVB's private `0x06` plus a registration
descriptor (`"AC-3"`/`"EAC3"`/`"DTS1"`) both resolve back to the right
`TsCodec` — matching `resolve`'s existing private-range handling rather than
adding a new one.

### DVB text

Every SI string may select its own character table with its first byte. The
default is ISO/IEC 6937, which is **not** Latin-1 and differs in about sixty
positions; treating it as Latin-1 is the usual mistake and gives visibly wrong
text for any accented service name.

Implemented: ISO 6937 including combining diacritics, ISO 8859-1/-9/-15,
UTF-16BE, UTF-8. **Not implemented**: ISO 8859-5 through -14 and the East
Asian tables. Those decode ASCII and emit `U+FFFD` for anything above `0x9F`,
deliberately — a name that is visibly broken gets reported and a name that is
quietly wrong does not. `decode_with_charset` returns which table was selected
so a caller can say which.

Combining diacritics are emitted as Unicode combining marks after their base
character rather than composed into precomposed code points, because
composition needs a normalisation table this crate does not carry. The result
is canonically equivalent but not byte-identical to an NFC renderer's.

## How to change it

* **Adding a `stream_type`** means one arm in `from_stream_type` and, if the
  codec is new, one variant in `TsCodec` with a `name`, a `media_type` and a
  `codec_id`. A test asserts the three agree wherever a `CodecId` exists.
* **Adding a descriptor** means a `TAG_` constant and, only if it changes
  output, an accessor. Resist the second half.
* **`TsCodec` exists because `CodecId` does not cover MPEG-TS.** See the gap
  list below. When `CodecId` grows, `TsCodec::codec_id` is the only function
  that changes.
* **Do not make `Section::new` infallible.** The partial-header case above is
  real input, and inventing a `version` of zero for it is how a corrupt PMT
  gets applied.
* **Gotcha — `0xFF` is stuffing, not a table.** A section can never start with
  it, so the assembler stops at the first `0xFF` between sections. A test
  fixture that uses `0xFF` as a `table_id` will silently frame nothing.
* **Gotcha — `section_length` is twelve bits but PSI tables cap at 1021.**
  `MAX_PSI_SECTION_LEN` records that; the assembler bounds by the buffer
  instead, deliberately, so a private section up to 4093 bytes still frames.
* **Adding a mux-side codec mapping** means one arm in `stream_type::for_codec`
  — pick the ATSC `stream_type` for `dvb == false` and, if the codec has no
  unambiguous 13818-1 assignment, a `0x06` + registration identifier for both
  branches. Add a case to `for_codec_round_trips_through_resolve` (or the
  AC-3-family test, if it needs the two-convention treatment) so drift from
  `resolve` fails a test instead of shipping.
* **Adding a table writer** should build on `write::build_section` rather than
  hand-rolling section framing again; that is the one place the header layout
  and the CRC placement are allowed to be decided.

## Configuration

No options and no features. Constants that are ours rather than the
specification's:

| Constant | Value | Basis |
|---|---|---|
| `MAX_SECTION_LEN` | 4096 | `3 + 4093`, the twelve-bit field's own ceiling |
| `MAX_PSI_SECTION_LEN` | 1024 | `3 + 1021`, the syntax-indicator cap |
| `PacketStride::MAX_STRIDE` | 204 | so a caller can size one stack buffer |

Everything else — the polynomial, the PID assignments, the table ids, the
`stream_type` table, the ISO 6937 code points — comes from ISO/IEC 13818-1 or
ETSI EN 300 468.

`time_base=1/27000000` on that demuxer, distinct from the 90 kHz
`TIME_BASE` the PES-reassembling `mpegts` demuxer uses.

## What `vaco-codec-core` does not cover

`CodecId` has grown since this note was first written — it now names AC-3,
E-AC-3, DTS, TrueHD, VC-1, Mpeg1video/Mpeg2video, Vvc, Cavs, Dirac, Mp1/Mp2
and HdmvPgsSubtitle among others, and both directions of this table use them:
`for_codec` (the muxer's question) always did, and `TsCodec::codec_id` (the
demuxer's question) now does too as of finding 4
(`planning/CONFORMANCE-FINDINGS.md`) — it used to map eight of the roughly
thirty `TsCodec` variants and fall through to `None`, i.e. `codec_name=unknown`
in `vaco-probe`, for the rest **even where `CodecId` already had a matching
variant sitting unused**: `mpeg2video`, `mp2`, `ac3`, `truehd` and others were
gaps in this function, not in that enum. Fixed by checking every variant
against the enum's actual contents rather than the eight originally wired up.

MPEG-TS still routinely carries **JPEG 2000, AVS2/AVS3, DVB subtitles, DVB
teletext, SCTE-35 splice information, timed ID3 and SMPTE KLV** — eight
`TsCodec` variants (`Jpeg2000`, `Avs2`, `Avs3`, `DvbSubtitle`, `DvbTeletext`,
`Scte35`, `TimedId3`, `Klv`) with genuinely no `CodecId` counterpart, and none
of which `vaco-mux-mpegts` can write for that reason either. Their names and
long names, probed from `ffmpeg -codecs` (8.1) rather than recalled, are in
`stream_type.rs`'s module docs for whoever adds them.

Collapsing them onto "unknown" would throw away the one fact the PMT actually
stated, so `TsCodec` carries the full repertoire and `TsCodec::codec_id()`
returns `None` where the workspace enum has nothing. `None` here means "this
codec is real and named; `vaco-codec-core` has no variant" — not "unknown
codec" — and the demuxer keeps reporting the stream, with its media type, its
PID and its language, under a `ts_codec` metadata tag.

Before finding 4 this was the single largest gap between this crate and the
reference's output, because `codec_name` is a printed field. The eight
variants above are the honestly-remaining piece of it; the rest was this
function not using what `vaco-codec-core` already had.

## Testing

* **91 tests**: 85 unit, 5 property, 1 doctest. (Was 82 before FM-25's writer
  module and `for_codec` landed.)
* **`tests/properties.rs` is `proptest`.** The two properties that carry the
  layer are round trips no finite case set can cover: a section survives *any*
  split across packets, and a CRC catches *every* single-bit error.
* **Fuzz target**: `mpegts_section` (D6). It reads its input as a sequence of
  `(payload_unit_start, payload)` pushes with the lengths taken from the input
  itself, so the fuzzer controls the packet *splitting* as well as the bytes,
  and every emitted section is offered to all four table parsers.
* **No new fuzz target for `write`.** Every function there takes typed,
  caller-constructed Rust values (a `u16` PID, a `Vec<PmtStreamOut>`) rather
  than attacker-controlled bytes — the untrusted-input direction is still
  entirely `psi`/`section`/`descriptor`, which `mpegts_section` already
  covers. `vaco-mux-mpegts`'s own `mpegts_mux_packet` fuzz target is what
  exercises this crate's writers under fuzzing, indirectly, on every call.

### What the generated tests found

**`abandoning_loses_one_section_and_recovers` (proptest), first run.**
`abandon()` kept the alignment, so the bytes after a continuity gap were framed
as sections. The shrunk counterexample was two sections of zeros: after the
gap the assembler emitted a four-byte section and then an unbounded run of
three-byte ones, all invented. Fixed by clearing alignment, which is now the
documented meaning of the method.

The same run also found that the *test's own muxer model* was wrong: a
continuation packet must stop short of the next section start, or that section
begins inside a packet with no `pointer_field` and no reader could find it. A
real muxer has the same constraint, so the model was fixed rather than the
assertion weakened.

**`mpegts_section` (fuzz), 30 executions in.** The target asserted that every
emitted section parses its own header. It does not: `01 80 00` is a long-form
section three bytes long. That is malformed input rather than a framing bug —
recorded above, and the assertion narrowed to "anything eight bytes or longer
parses", which is the real invariant.
