# Fuzz corpus and crash-input minimisation

## What it is

Two additions that close the "corpus minimisation" half of issue #571
(XF-02), which the fuzz targets themselves did not cover:

- **`just corpus-minimise TARGET`** — coverage-guided corpus shrinking,
  wired to `cargo fuzz cmin`.
- **`just semantic-min TARGET FILE`** (`fuzz/src/bin/semantic_min.rs`) — a
  structure-aware minimiser for one crashing input, for the container
  formats named in that issue (MP4/ISO base media, Matroska/EBML,
  MPEG-TS) plus a byte-level fallback for everything else.

Neither existed before: `fuzz/Cargo.toml` had 175+ libFuzzer targets but no
recipe or tool touched minimisation at all.

## How it works

### `corpus-minimise` — coverage-guided, byte-level

A thin wrapper around `cargo +nightly fuzz cmin <target> --no-default-features
--features <feature>`, using the same `fuzz-feature` lookup `fuzz`/`fuzz-all`
already use to isolate a target's own crate from an unrelated one that does
not currently build. `cmin` runs the target's own binary under
`-merge=1`, keeping only the files in `fuzz/corpus/<target>` that add new
coverage, in corpus-file order. It cannot understand structure — a corpus
file that trips a new code path stays whole or is dropped whole, byte-level
deletion is not attempted.

### `semantic_min` — structural, for one crash at a time

Coverage minimisation and crash minimisation are different problems.
`cmin`/`tmin` only ever try deleting contiguous byte ranges and re-checking
whether the input is still "interesting". For a length-prefixed container
that is slow: deleting part of a box's payload almost always leaves the box
header's own stated size disagreeing with the real bytes, so the shrunk
candidate is usually rejected even when the crash has nothing to do with the
deleted bytes.

`semantic_min` instead:

1. Confirms the input reproduces a crash in `target`, by replaying it
   exactly the way `fuzz/seeds/README.md` documents replaying one:
   `cargo +nightly fuzz run <target> --no-default-features --features
   <feature> <file>`, non-zero exit = reproduction.
2. Parses the input's container structure — ISO base media boxes
   (`isom::parse`) or EBML elements (`ebml::parse`), chosen by the target's
   name (`--format` overrides this) — and repeatedly removes the largest
   node that keeps the crash reproducing, **patching every ancestor's
   stored size field by the removed length in the same edit**. This is the
   thing `cmin`/`tmin` cannot do: dropping a whole box or element instead of
   a byte-by-byte crawl through it.
3. MPEG-TS has no length field to fix up (fixed 188-byte packets), so its
   "structural" pass is just whole-packet-aligned deletion.
4. Falls back to a byte-level delta-debugging pass (`byte_ddmin`, the
   classic Zeller–Hildebrandt ddmin algorithm) for whatever the structural
   pass could not explain — padding inside a kept box's payload, an
   unnecessary run of bytes in a string option, and so on.
5. Re-verifies the final result against the oracle once more before writing
   it, so a bug in the reduction bookkeeping fails loudly instead of
   silently shipping a "minimised" file that no longer reproduces anything.

Every accepted edit is itself oracle-checked (a real subprocess run of the
real target), so a wrong structural guess — e.g. treating an EBML element's
unknown-size marker as "extends to end of container" when the real boundary
is narrower per RFC 8794 §6.2's termination rules — only ever costs a
rejected candidate, never an incorrect one.

## How to change it

- **Add a container format**: write a `parse(buf: &[u8]) -> Node` function
  (see the `isom`/`ebml` modules in `semantic_min.rs`) that returns a tree
  of removable byte ranges, each optionally carrying a `SizeField` describing
  where and how wide its parent's stored size is. Wire it into `infer_format`
  and the `match format` in `run`.
- **The byte-level fallback** (`byte_ddmin`) is intentionally a from-scratch
  reimplementation of the same algorithm `vaco-corpus::mutate::minimise`
  already provides for the differential harness, not a dependency on it —
  see the module doc's "Why this exists" section for why `fuzz/Cargo.toml`
  cannot carry that dependency (it is entirely generated by `cargo xtask
  gen-fuzz` from `fuzz_targets/*.rs` front-matter, which knows nothing about
  `fuzz/src/bin/`). If a genuine shared crate for both call sites is ever
  worth the coupling, that dependency has to be added as a plain
  (non-optional) dependency **outside** the generated region of
  `fuzz/Cargo.toml`, and `gen_fuzz.rs` taught to leave that region alone.
- **Gotcha**: `semantic_min` builds and runs the target via `cargo +nightly
  fuzz`, which uses `fuzz/target/` — the same shared build directory every
  other `just fuzz`/`fuzz-all` invocation uses. That is consistent with how
  those recipes already behave, not a new sharing hazard.

## Configuration

- `semantic_min <target> <file> [--out PATH] [--feature NAME] [--format
  mp4|ebml|ts|none]`. `--format` overrides the name-based guess in
  `infer_format` for a target this tool does not recognise.
- `corpus-minimise` takes only `TARGET`; it operates on
  `fuzz/corpus/<target>` (created if missing).

## Dependencies

Neither tool depends on any `vaco-*` crate — see `semantic_min.rs`'s module
doc for why. Both need a `nightly` toolchain and `cargo-fuzz` installed,
exactly like every other `fuzz`/`fuzz-all`/`fuzz-check` recipe in this
repository (`rustup toolchain install nightly` and `cargo install cargo-fuzz
--locked`).
